# 变更快照的小文件 I/O 方案

本轮目标是减少创建、打开和删除大量小文件的开销。磁盘占用需要另外处理，因为把相同的快照字节装进更少的文件，并不会自动减少保留的内容总量。

## 当前存储实际做了什么

`WorkspaceChangeStore.putBlob` 对完整内容计算 SHA-256，使用哈希作为 `workspace_changes/v1/objects` 下的文件名。相同内容在不同文件、操作和对话之间共享一个对象；只有新的哈希才创建对象文件。`writeAtomic` 使用临时文件和替换保护完整性，因此每次新内容还涉及目录项更新与原子写入。不能把“修改一百次”直接等同于“必然创建一百个快照文件”，因为重复内容已经去重。

`operations` 另外按操作保存 JSON。工作区观察清单和终端 SQLite 索引都引用对象哈希。删除操作记录时，`removeRecords` 同时核对其他操作、工作区基线和终端索引的引用，才能回收不再使用的内容。修改对象格式必须保留这套共享引用语义，不能只改文件写入入口。

前次只读取证记录过 objects 约 14,427 个、合计约 352 MiB。这是历史观测，不是本轮重新扫描结果。本轮没有扫描或清理设备上的真实快照，也没有执行存储性能基准。

## 方案一：按容量追加分卷

可行。建议使用接近 1 MiB 的目标分卷，将对象记录依次追加到当前卷，达到目标后封卷。500 KiB 也能实现，但会更频繁地创建卷文件。1 MiB 是待测的起始参数，不是已证明最优的容量。

对象记录应包含格式版本、哈希、长度、校验和与完整内容；独立索引保存“哈希 → 分卷编号、偏移、长度”。现有调用方继续按哈希读取，无需按原文件寻找历史。可以沿用项目已有的 SQLite 能力维护索引，批量提交索引更新，避免每次追加都重写整个索引文件。

关键取舍如下：

- 新内容追加到少数已打开的文件，减少对象文件和临时文件的创建；索引更新和数据写入仍然存在
- 保留全局哈希去重，多个文件共享相同快照的行为不变
- 现有单快照上限是 2 MiB，可能大于分卷目标；应把它写入独立的大对象卷，而不是直接拒绝合法快照或拆成无法独立校验的半条记录
- 写入顺序应为完整记录落盘，再提交索引；启动恢复能识别并截去未完成的尾部，不能让索引指向半条数据
- 删除引用先标记对象不再使用，空间通过受限的卷压缩回收；这会用顺序读写换取较少的目录操作，但也会产生写放大
- 用户删除整个 objects 目录后，索引引用应明确视为内容已清理；删除部分卷会影响其中多个对象，界面需继续保留仍可读取的记录

若总内容完全相同且没有卷内空隙，仅以 352 MiB 除以目标容量估算，1 MiB 对应约 352 卷，500 KiB 对应约 721 卷。这只是容量比例，实际数量还受记录头、对象大小、封卷余量、大对象和未回收空间影响，不能据此宣称已经获得相应的性能提升。

## 方案二：同一原文件的所有版本聚合

也可实现，但“聚合”应采用追加版本记录和偏移索引。每次修改都重新序列化或覆盖整个历史文件，会让后期写入量随历史增长，抵消减少文件创建的收益。

它的好处是某个文件的历史通常连续存放，读取和整组删除比较直接。主要复杂度在于原文件的身份：同一路径可以先删除再创建，同一文件也可以重命名；Android 与 Ubuntu 共享存储还有路径别名。现有 `historyLocation` 解决的是路径归一，并没有提供跨重命名的永久文件 ID。

不同对话可以引用同一内容，某个基线也可能长期引用旧版本。如果按原文件复制全部版本，会失去跨文件去重；如果继续共享全局哈希索引，又必须处理一个聚合文件被删除后其他文件仍引用其中内容的情况。部分版本删除同样需要压缩与重写，不能直接移除包含它的整份聚合文件。

当大量文件各修改一次时，它仍然会创建大量聚合文件，收益主要集中在“少数文件反复修改”的场景。因此，它与当前覆盖多个工作区和终端路径的采集方式并不完全匹配。

## 建议与实施边界

建议后续优先验证方案一：约 1 MiB 的追加分卷、全局哈希索引、按引用回收以及空闲时受预算约束的压缩。对象查询接口可以先抽成 `put/read/contains/removeReferences`，让记录器和基线继续使用同一哈希身份。若希望先减少自定义分卷与恢复逻辑，SQLite 的独立 BLOB 表也值得作为对照，但其 WAL、事务批次和大对象读写仍须测量。

迁移应使用新的格式版本，复制并校验旧对象后才切换引用，不原地覆盖现有 objects；需要覆盖中断恢复、旧索引一致性、完整与部分外部删除、跨对话共享和压缩取消。该迁移不在本轮实现范围内。

测量至少应覆盖少数文件频繁修改、大量小文件各修改一次、重复内容高比例、接近 2 MiB 的大快照和删除后的回收。比较创建文件次数、系统调用、写入字节、耗时分位数、峰值内存、恢复时间与回收后占用。没有这些数据前，仅能确认结构上可减少小文件数量，不能声称已解决全部 I/O 或空间问题。

如果首要目标是限制累计占用，后续还应单独设计保留时长或容量配额，并明确哪些操作和基线可以删除；分卷大小不能代替保留策略。
