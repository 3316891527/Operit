# 五千与两万个对象的堆和 I/O 对照

5,000 与 20,000 个不同的 1 KiB 对象，在本次临时目录对照中均由分卷更快写完。但分卷的采样已用堆没有降低，累计线程分配和写入计数增加。这个结果支持分卷对大量小快照的文件数量与写入耗时有价值，不能据此声明 Android 应用的内存溢出已解决。

## 方法与边界

基于 PR #253 的分卷核心。后续 c7cab89c 只修正 Android 目录同步公开 API，不改卷和位置索引核心。使用同一设备 Ubuntu 中的 JDK 17、真实临时文件和 SQLite JDBC，分别测 5,000、20,000 个全不相同的 1,024 字节对象，内容逐个生成，不保存全量字节或哈希列表。

每组使用独立 JVM，参数为 -Xms16m、-Xmx64m、UseSerialGC、ActiveProcessorCount=1，串行运行四组。每个 JVM 先预热相同的独立文件和分卷路径，再开始计量。5,000 组先分卷后独立文件，20,000 组先独立文件后分卷；每种配置只测一轮，没有随机交叉与统计显著性分析。没有清理系统页缓存，结果不是整个应用或 ART 的性能结论。

独立文件使用哈希命名、临时文件 fd.sync 与原子移动。分卷直接调用生产 SnapshotPackStore 和 SnapshotPackIndex，位置库 FULL 同步，WAL 自动检查点 256 页，当前卷每条对象同步。独立文件没有额外目录同步，新路径还包括目录和 SQLite 持久化，工作量有差异。

已用堆每 128 次写入采样，报告采样最大值，不等于精确堆峰值。通过回收后读数观察对象库保持打开时的存活堆，累计分配来自 ThreadMXBean。它们均不包含完整原生 SQLite 内存、内核目录项和页缓存。两条路径的主动 GC 时间从耗时中扣除，GC 次数和时间记录自然回收，不计主动回收。

I/O 从基准进程自己的 /proc/self/io 读取。wchar 为写调用交付的字节数，syscw 为写调用次数，write_bytes 为内核计入该进程的存储写入字节，不等于实际闪存写入量，也不覆盖所有目录与文件系统元数据成本。写后重新打开并抽样核对 64 个对象，校验不计入写入耗时和 I/O 计数。

临时数据位于观察器排除的目录，避免测试对象再次进入应用操作历史。每组结束删除自己的负载文件；本轮没有迁移或清理真实快照，没有进行全设备压力取证。

## 5,000 个不同对象

以下数值均为独立文件 → 分卷：

- 内容文件数量：5,000 → 6 个卷，加索引后分卷共 7 个文件
- 写入耗时：17,856.239 → 9,809.219 ms，本轮约缩短 45%
- 文件逻辑长度合计：5,120,000 → 6,667,680 字节
- 采样最大已用堆：6.840 → 6.854 MiB
- 对象库打开且 GC 后的已用堆：2.343 → 2.407 MiB
- 累计线程分配：15.787 → 33.289 MiB
- 自然 GC 次数与累计时间：3 次 / 6 ms → 7 次 / 5 ms
- 写调用次数：5,000 → 98,816
- 写调用字节 wchar：4.883 → 112.085 MiB
- 内核计入的 write_bytes：79.320 → 332.359 MiB

## 20,000 个不同对象

以下数值均为独立文件 → 分卷：

- 内容文件数量：20,000 → 21 个卷，加索引后分卷共 22 个文件
- 写入耗时：66,861.886 → 35,663.347 ms，本轮约缩短 47%
- 文件逻辑长度合计：20,480,000 → 26,646,096 字节
- 采样最大已用堆：6.848 → 6.879 MiB
- 对象库打开且 GC 后的已用堆：2.261 → 2.418 MiB
- 累计线程分配：49.024 → 124.747 MiB
- 自然 GC 次数与累计时间：11 次 / 10 ms → 28 次 / 21 ms
- 写调用次数：20,000 → 408,817
- 写调用字节 wchar：19.531 → 493.329 MiB
- 内核计入的 write_bytes：319.813 → 1,416.469 MiB

两条路径都在 64 MiB 堆限制下完成，没有复现内存溢出。累计分配超过堆上限表示对象被反复分配和回收，不是同时常驻 124.747 MiB。这个对象库基准不包含完整操作记录、界面、源文件扫描、差异计算与消息内容，不能用其低堆读数代表整个应用。

## 哪些开销随文件数量增长

分卷合并的是快照副本。任务产生的两万个源文件仍按既有规则创建、监听和扫描，变化内容仍需读取与哈希，不能把快照对象数量下降当作源文件开销也消失。旧独立对象写入本身也逐个处理，没有在该函数里常驻所有内容；合并文件不能自动减少一份不存在的全量堆缓存。

当前分卷每个不同对象仍执行卷 fd.sync 和 SQLite 事务，驱动、查询与位置记录会分配临时对象，SQLite 位置缓存最多 256 项。WAL、检查点和卷头写入还会放大写调用与写入字节。文件数量减少后本轮耗时确实下降，但耗时、I/O 写入量与 JVM 分配量并不是同一个指标。

另有一条确定存在的全量元数据路径：[TerminalFileJournal.save](../../../../app/src/main/java/com/ai/assistance/operit/ui/features/conversation/workspace/changes/TerminalFileJournal.kt) 每批先读取该执行积累的全部记录，构造关联映射，再让 [WorkspaceChangeStore.replaceOperation](../../../../app/src/main/java/com/ai/assistance/operit/ui/features/conversation/workspace/changes/WorkspaceChangeStore.kt) 将整份清单重新编码成 JSON 字符串、UTF-8 字节并原子写入。TerminalObservationIndex 的差异页上限为 128 条，分页读取差异没有使这个保存过程也成为增量保存。

作为条数计算示例，如果同一个活动执行按每批 128 条持续新增到 20,000 条、不合并回改，整份 JSON 累计重新序列化约 1,587,488 条次，约为最终记录数的 79 倍。这是根据现有保存调用计算的示例，不是测到的字节量或真实任务事件数。实际写入体积取决于字段长度、分组、事件批次和同一文件的反复修改。

WorkspaceChangeStore.operationRecords 还会产生整份文本与反序列化列表，保存路径再构造映射、列表、JSON 字符串和字节数组；历史查询 records 会读取并解析操作 JSON 后过滤和排序。这些全量元数据及差异读取可能放大堆峰值和 I/O，分卷没有覆盖它们。本轮没有 OOM 堆栈或堆快照，不能认定它们是设备上那次内存溢出的唯一原因。

## 后续优先级

- 将活动操作记录的保存和历史查询改成增量落盘、按需分页，避免每批重新处理全部旧记录
- 为快照增加明确的批量持久化边界，减少每对象事务与同步；仍须先持久化内容与位置，再发布引用记录
- 按需生成差异，控制界面同时持有的记录与文本规模，再在完整任务中验证 ART 堆与原生内存

本轮只交付 Android 公开 API 编译修复与测量报告，没有改变上述元数据保存、事务边界或历史查询行为。原先的小样本见 [临时目录对照](measurement.md)，卷格式见 [格式与生命周期](format.md)。
